# Отдельный сервер знаний для внешних клиентов

Сервис работает независимо от фронтенда и Go-приложения. Клиент получает HTTPS URL
и собственный Bearer-токен. Поддерживается Streamable HTTP MCP и обычный HTTP поиск.
MCP возвращает источники; ответ генерирует LLM клиента. Покупать или менять LLM для
подключения не нужно. Поиск использует BGE-M3 через Ollama, генератор Qwen не требуется.

## Границы профиля

Один экземпляр сервиса и БД предназначены для одной организации. Это не мультитенантный
SaaS. Для другой организации запускайте отдельный экземпляр с отдельным томом БД.
`common` доступен всем читающим клиентам этого экземпляра; `team` — только явно
перечисленным командам. Персональные internship-данные сервисным клиентам недоступны.
`documents:write` — административное разрешение на весь корпус организации, включая
права документов. Не выдавайте его обычному агенту.

Реализован частный профиль авторизации с заранее выданными ключами, сроком действия
и scopes. OAuth discovery, SSO и делегирование от имени сотрудников пока не реализованы.
Клиент должен поддерживать передачу Authorization заголовка. Подключение OAuth-only
клиентов требует дальнейшей интеграции с корпоративным IdP; текущий профиль не выдаёт
себя за стандартный OAuth. SDK поддерживает протоколы до 2025-11-25; более новые
версии и конкретные desktop-клиенты нужно проверять отдельно.

## Развёртывание

Нужны Docker Compose, домен с DNS на сервер, доступные TCP 80/443 для Caddy и TLS.
На сервер загружается репозиторий; потребителям сервиса репозиторий не нужен.

1. Скопируйте `knowledge/external.env.example` в `.env.external` в корне репозитория.
2. Выполните `python knowledge/examples/keygen.py` отдельно для reader и writer.
   Передайте полученные токены владельцам клиентов, а в конфигурацию положите только
   SHA-256. Задайте домен, случайный пароль БД (URL-safe), отдельный случайный
   RAG_SERVICE_TOKEN длиной от 24 символов и будущий срок действия клиентов.
3. Запустите из корня:

```sh
docker compose --env-file .env.external -f docker-compose.knowledge.yml up -d --build
docker compose --env-file .env.external -f docker-compose.knowledge.yml exec ollama ollama pull bge-m3:567m
```

Worker автоматически создаёт схему и опрашивает сохраняемую очередь раз в 5 секунд.
БД, Ollama и внутренние API не публикуются наружу; gateway пропускает только `/mcp/`
и `/v1/`. Ограничение тела запроса — 1 MB. Нагрузочные квоты на клиента пока не
реализованы. Параметры allowed_hosts/origins задаются явно, защита MCP от DNS rebinding
сохранена. Для browser-клиентов требуется отдельная настройка CORS; пример рассчитан
на серверных клиентов. Access-логи приложения выключены; не включайте запись Authorization.

Первый документ можно загрузить API ниже. Дополнительно можно импортировать Playbook:

```sh
docker compose --env-file .env.external -f docker-compose.knowledge.yml exec knowledge python -m homych_knowledge.ingest playbook
```

Команда Playbook заменяет весь корпус, поэтому используйте её только для первичной
загрузки, до подключения потока корпоративных изменений. При обновлении существующего
старого стенда выполните миграцию и повторный импорт: прежние снимки не содержат
исходные JSON документов, необходимые очереди. Перед миграцией сделайте backup БД.

## Подключение агента

URL: `https://YOUR_DOMAIN/mcp/` (с завершающим slash).
Транспорт: Streamable HTTP. Заголовок: `Authorization: Bearer CLIENT_TOKEN`.
Scopes читателя: `knowledge:search`, дополнительно `knowledge:read` для полного источника.
Точное поле настройки URL/headers зависит от MCP-клиента.

Пример Python с настоящими initialize/list_tools/call_tool: `examples/client.py`.
Из каталога `knowledge` с установленными зависимостями:

```sh
MCP_URL=https://YOUR_DOMAIN/mcp/ MCP_TOKEN=CLIENT_TOKEN python examples/client.py
```

В PowerShell задайте `$env:MCP_URL` и `$env:MCP_TOKEN` перед запуском Python.
Доступны `search_knowledge(query, limit=5)` и
`get_knowledge_document(documentId, revision)` — до 20 фрагментов точной активной
версии. Пустая выдача не раскрывает, существует ли закрытый/устаревший документ.
Аннотации инструментов указывают на чтение; они не заменяют серверную проверку scopes.

Для приложений без MCP:

```sh
curl https://YOUR_DOMAIN/v1/search -H "Authorization: Bearer READER_TOKEN" \
  -H 'Content-Type: application/json' -d '{"query":"Как устроено обучение?","limit":5}'
```

## Пополнение и синхронизация

API принимает нормализованный JSON `examples/document.json`. Конвертация PDF/DOCX,
коннекторы корпоративных порталов и автоматическая периодическая синхронизация Git
в эту итерацию не входят. Коннектор Авито отправляет изменения через API:

```sh
curl -X PUT https://YOUR_DOMAIN/v1/documents/corporate-onboarding \
  -H "Authorization: Bearer WRITER_TOKEN" -H 'Idempotency-Key: onboarding-v1' \
  -H 'Content-Type: application/json' --data-binary @knowledge/examples/document.json
# HTTP 202: {"jobId":"job-...","status":"pending"}
curl https://YOUR_DOMAIN/v1/jobs/JOB_ID -H "Authorization: Bearer WRITER_TOKEN"
curl -X DELETE https://YOUR_DOMAIN/v1/documents/corporate-onboarding \
  -H "Authorization: Bearer WRITER_TOKEN" -H 'Idempotency-Key: onboarding-delete-v1'
```

Для обновления отправьте тот же documentId, новую revision и новый Idempotency-Key.
Повтор идентичного запроса с прежним ключом возвращает прежний jobId; другой payload
с тем же ключом — 409. Ключи хранятся в PostgreSQL и переживают перезапуск.
Один revision неизменяем: текст, ACL и метаданные менять без новой revision нельзя.

Сразу после постановки изменения/удаления старая версия скрывается из поиска.
Worker сериализует публикации, переиспользует эмбеддинги совпадающего текста и той же
модели, а затем атомарно переключает снимок и завершает job. Сбой оставляет старый
снимок для остальных документов, изменяемый документ остаётся скрытым.
Статусы: pending, processing, failed, completed. После трёх попыток очередь останавливается
на ошибке; оператор исправляет причину, затем вызывает POST /v1/jobs/JOB_ID/retry с ключом создавшего job клиента. Это сознательная остановка, чтобы более новые версии не обгоняли
необработанную старую. Перезапуск worker возобновляет незавершённый job.
GET job разрешён только создавшему его клиенту; технические ошибки не содержат текстов.

При отзыве client key удалите запись из RAG_EXTERNAL_CLIENTS и пересоздайте knowledge
и worker. При ротации сначала добавьте нового клиента, переключите потребителя, затем
удалите старого. Истечение expires_at проверяется на каждом запросе.

## Рост базы и проверки

Неизменившийся текст не эмбеддится повторно, но текущая публикация создаёт полный
новый снимок, копируя векторы. Исторические снимки и jobs автоматически не удаляются;
для большого корпуса понадобятся политика хранения, пакетная публикация и замеры
ANN-индекса. Смена embedding-модели требует переиндексации всего корпуса. Текущее
решение не заявляет неограниченную масштабируемость.

Проверки: реальные SDK MCP initialize/list/call, scopes и expiry, сервисная identity
без Go, PostgreSQL jobs/idempotency, обновление/удаление, повторное использование
векторов. Тесты запускаются из knowledge: `uv run pytest`; интеграционные — при
заданном TEST_DATABASE_URL для PostgreSQL с pgvector и правом CREATE DATABASE.
Полный путь через TLS gateway проверяется после развёртывания на реальном домене.

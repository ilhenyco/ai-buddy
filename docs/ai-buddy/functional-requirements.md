# Функциональные требования продукта Хомыч

Версия 0.4 · 12 ноября 2026 года · Рабочая редакция для команды разработки

Версия 0.4 от 12 ноября 2026 года. Рабочая редакция для команды разработки. Документ фиксирует уточнённую концепцию и отделяет согласованные функции от предложений и открытых вопросов.

Продукт сопровождает стажёра через переписку с ботом. По периодам стажировки он получает сообщения с чек-листами, инструкциями и ссылками. Бадди и руководитель получают соответствующие сообщения о своей помощи стажёру. Руководитель собирает сценарий из готовых блоков.

## Основа текущей концепции

Свободным диалогом с AI пользуется стажёр. Для бадди и руководителя предусмотрены сообщения по сценарию. Их отдельный AI чат в текущую концепцию не включён.

Roadmap приходит циклами в сообщениях. Чек-листы нужны для напоминаний и формального учёта. Их заполнение не управляет переходом на следующий этап.

Большинство действий выполняется по ссылкам во внешних инструментах при поддержке бадди. Результаты и выводы встреч участники готовят вне продукта.

Знания для ответов находятся через RAG — поиск подходящих фрагментов в подготовленных материалах. Расписание и получатели сообщений определяются опубликованным сценарием.

Личные вопросы стажёра и ответы AI остаются в его переписке. Бадди и руководитель получают самостоятельные плановые сообщения о своих действиях по соответствующим пунктам стажёра.

Область документа — функциональность полной версии продукта. Актуальная граница локального FRONT и предложенный порядок рабочего MVP описаны в team-specification.md; промышленный объём требует отдельных решений. Новые кабинеты, кадровые интеграции и проверка результатов встреч не считаются автоматически согласованными.

Обозначения. Согласовано — явно следует из решений пользователя. Предложение — конкретизация для разработки, требующая решения команды. Открытый вопрос — поведение пока нельзя однозначно реализовать. Подробные карточки всех функций FRONT: frontend-functional-specification.md; матрица связей: traceability.csv. Новые ID в этом документе заменяют рабочий перечень FR из чата; прежние ID нельзя сопоставлять по номеру без проверки текста.

## Настройка сценария руководителем

Конструктор — отдельный сценарий руководителя. Собранный план задаёт расписание сообщений участникам конкретной стажировки. Возможность применять один шаблон массово остаётся открытым вопросом OQ06.

### FR-PL-01 Выбор шаблона

Система должна позволять руководителю выбрать шаблон стажировки длительностью 6 или 9 месяцев.

**Проверка.** При создании сценария доступны оба варианта. Выбранный вариант определяет исходный набор периодов.

**Статус:** Согласовано.

### FR-PL-02 Назначение участников

Руководитель должен иметь возможность связать сценарий со стажёром и назначить бадди. Система должна знать руководителя этой стажировки.

**Проверка.** Сценарий содержит конкретных получателей сообщений для ролей стажёра, бадди и руководителя.

**Статус:** Согласовано.

### FR-PL-03 Сборка из готовых блоков

Руководитель должен иметь возможность добавлять и располагать готовые блоки стажировки, настраивать их сроки и содержание сообщений.

**Проверка.** Добавленный блок отражается в черновике с периодом и сообщениями для соответствующих участников.

**Статус:** Согласовано.

### FR-PL-04 Содержание блока

Блок должен связывать событие или период с сообщением стажёру и соответствующими сообщениями бадди и руководителю, когда требуется их участие.

**Проверка.** Блок получения доступов содержит инструкцию стажёру и отдельные инструкции по помощи для назначенных участников.

**Статус:** Согласовано.

### FR-PL-05 Предпросмотр и публикация

Руководитель должен иметь возможность просмотреть подготовленный сценарий и опубликовать его. Опубликованная версия становится основанием рассылок.

**Проверка.** Предпросмотр показывает тексты, сроки и адресатов. Неопубликованный черновик не запускает сообщения.

**Статус:** Согласовано.

### FR-PL-06 Проверка перед публикацией

Система должна проверять наличие участников, условий отправки и обязательного содержания блока перед публикацией.

**Проверка.** При отсутствии адресата или условия отправки система показывает конкретную проблему и сохраняет черновик.

**Статус:** Согласовано планом от 12 ноября 2026 года.

### FR-PL-07 Изменение опубликованного сценария

Изменение сценария должно создавать новую версию, по которой обновляются ещё не отправленные сообщения. Ранее отправленные сообщения сохраняются в истории.

**Проверка.** После переноса будущего периода используется новое расписание. Повтор прежней рассылки не возникает.

**Статус:** Согласовано планом от 12 ноября 2026 года.


### FR-PL-08 Список сценариев и возврат к черновикам

Вкладка «Сценарий» руководителя открывает список персональных сценариев разных стажёров. В списке доступны название, стажёр, длительность, дата начала, изменение и состояние. Поиск работает по названию и стажёру. Фильтры: «Все», «Черновики», «Опубликованные». Опубликованная запись с правками входит также в черновики. Нажатие открывает её рабочую редакцию.

**Проверка.** После создания двух черновиков, перехода в список и перезагрузки каждый открывается с собственными данными. «К списку сценариев» и вкладка возвращают в список.

**Статус:** Согласовано 12 ноября 2026 года.

### FR-PL-09 Несколько вариантов для одного стажёра

У одного стажёра может быть несколько персональных вариантов. Только один используется для сообщений. Публикация другого варианта явно предупреждает о замене; прежний остаётся в списке с отметкой «Не используется». У действующего — «Используется для сообщений». Вводится редактируемое название сценария. Уже опубликованный вариант сохраняет своего стажёра.

**Проверка.** Публикация варианта B стажёру A заменяет только его действующий вариант, не затрагивая планы другого стажёра. Старые сообщения и отметки остаются; при замене не досылаются блоки с датой не позднее даты переключения.

**Статус:** Согласовано 12 ноября 2026 года; граница досылки реализована в локальном прототипе как дата переключения.

### FR-PL-10 Автосохранение рабочих редакций

Черновики, включая неполные, сохраняются автоматически. Кнопка «Сохранить черновик» выполняет повторное сохранение и подтверждает только успешную запись. Видно время сохранения. Ошибка не удаляет данные открытой вкладки, отображается с повторной попыткой. Валидация публикации не мешает сохранять неполный черновик. Правки опубликованного плана не меняют расписание до публикации.

**Проверка.** Сохранить черновик без участника или даты, открыть после перезагрузки; при ошибке записи не показывать успешное сохранение и разрешить повторить запись тех же данных.

**Статус:** Согласовано 12 ноября 2026 года.

### FR-PL-11 Разделение истории по стажёрам

Переписка, отметки, события и снимки плановых сообщений связаны со стажёром; события содержат ID варианта сценария. При смене действующего варианта история не сбрасывается и не пересылается заново. При ответе AI после переключения демонстрационного пользователя результат записывается исходному стажёру.

**Проверка.** Вопросы и отметки стажёра A отсутствуют у B; черновик не запускает сообщения. Данные прежней версии локального прототипа переносятся без потери и без удаления исходной записи.

**Статус:** Согласовано 12 ноября 2026 года. Хранение в браузере и переключатель просмотра являются средствами демонстрации, а не промышленной авторизацией.


## Переписка и действия стажёра

Переписка объединяет вопросы к AI и сообщения по этапам. Отдельный экран личного кабинета не является обязательной частью текущей концепции. Способ различать два типа сообщений в интерфейсе ещё предстоит спроектировать.

### FR-IN-01 Получение сообщения чек листа

Система должна отправлять стажёру сообщение с действиями на наступивший период стажировки.

**Проверка.** При наступлении периода стажёр получает предназначенный ему текст из опубликованного сценария.

**Статус:** Согласовано.

### FR-IN-02 Инструкция к действию

Сообщение должно объяснять действие стажёра и содержать предусмотренные сценарием ссылки, сроки и контакт участника, который помогает.

**Проверка.** Из сообщения о доступах понятно, куда перейти и с каким бадди выполнить действие.

**Статус:** Согласовано.

### FR-IN-03 Вопрос к AI

Стажёр должен иметь возможность написать вопрос в диалоговое окно и получить ответ по доступным ему материалам.

**Проверка.** Вопрос о корпоративном инструменте обрабатывается с использованием разрешённых источников и контекста его стажировки.

**Статус:** Согласовано.

### FR-IN-04 Отметка пункта

Если в сообщении предусмотрены отметки, стажёр должен иметь возможность отметить пункт чек-листа. Отметка служит для учёта и не запускает переход этапа.

**Проверка.** Отметка меняет только состояние соответствующего пункта. Расписание следующих периодов остаётся прежним.

**Статус:** Согласовано.

### FR-IN-05 Просмотр истории

Система должна сохранять переписку и отправленные стажёру сообщения, чтобы он мог вернуться к инструкциям и ссылкам.

**Проверка.** После повторного входа доступны прежние сообщения и сохранённые отметки.

**Статус:** Предложение.

### FR-IN-06 Переход по ссылке

Стажёр должен иметь возможность открыть ссылку на внешний инструмент или материал из сообщения бота.

**Проверка.** Нажатие открывает указанный ресурс. Сам переход не фиксирует получение доступа, прохождение курса или выполнение работы.

**Статус:** Согласовано.

Пример. Бот сообщает: «На этой неделе получи доступы. Открой инструкцию и форму заявки. Пройди этот шаг вместе с назначенным бадди». Стажёр может уточнить назначение инструмента у AI, а само действие выполняет по ссылке.


### FR-IN-07 Случайные подсказки текущего этапа

Продукт автоматически показывает стажёру три разных вопроса из встроенного набора его текущего этапа. Руководитель не настраивает подсказки. Набор выбирается случайно при смене этапа, сохраняется отдельно для каждого стажёра и не меняется после ответов, отметок, перезагрузки, просмотра истории или правок черновика. Этап определяется датами действующего опубликованного сценария; публикация без смены этапа не обновляет вопросы. До старта показываются стартовые вопросы, без опубликованного сценария подсказки скрыты. Копии готовых блоков наследуют их тему.

Нажатие отправляет выбранный вопрос обычным сообщением в личный чат. Стажёр может написать другой вопрос. Вопросы про отгул и отпуск не ограничены этапом; отсутствие соответствующей инструкции приводит к честному сообщению и направлению к HR, без выдуманных правил.

**Проверка.** На каждом этапе три неповторяющихся вопроса из его набора. Перезагрузка, ответ и отметка сохраняют выбор; смена этапа обновляет его. Проверить 6/9 месяцев и перенос дат, независимость стажёров, отсутствие кнопок у бадди/руководителя, совместимость v3 и мобильную прокрутку. Полные наборы: утверждённое [решение](decisions/2026-11-12-stage-suggestions.md) и `frontend/src/suggestions.ts`.

**Статус:** Согласовано 12 ноября 2026 года.


## Периоды и формальные чек листы

Период — временная часть стажировки. Чек-лист — перечень напоминаний для участника. Состояние периода и состояние отметок учитываются раздельно.

### FR-CY-01 Переход по расписанию

Наступление следующего периода должно определяться датами опубликованного сценария и не зависеть от заполнения чек-листов.

**Проверка.** При незаполненном чек-листе предыдущего периода сообщения следующего периода отправляются по расписанию.

**Статус:** Согласовано.

### FR-CY-02 Свободное движение по этапам

Незаполненные пункты не должны блокировать сообщения следующих периодов или требовать подтверждения руководителем либо бадди для перехода.

**Проверка.** Стажёр получает подготовку к экватору, даже если знакомство с командой осталось неотмеченным.

**Статус:** Согласовано.

### FR-CY-03 Достоверность отметок

Система не должна автоматически отмечать пункт выполненным из-за наступления нового периода, отправки сообщения или открытия внешней ссылки.

**Проверка.** При отправке следующего сообщения прежние отметки сохраняют своё фактическое состояние.

**Статус:** Согласовано.

### FR-CY-04 Привязка к датам

Для вычисления расписания сценарий должен содержать дату начала и согласованную временную зону. Правила расчёта месяцев и границ периодов задаются отдельно.

**Проверка.** Для опубликованного сценария можно однозначно определить плановое время сообщения. Конкретные календарные правила согласуются в OQ04.

**Статус:** Предложение.

### FR-CY-05 Формальная отметка и внешнее событие

Система должна различать отметку чек-листа и подтверждённое состояние внешней операции, если такая интеграция используется.

**Проверка.** Галочка «Получить доступ» не создаёт заявку и не присваивает статус одобрения.

**Статус:** Согласовано.

### FR-CY-06 Отметка прошедшего периода

Система должна позволять изменить собственную отметку в чек-листе прошедшего периода без повторного запуска его рассылки.

**Проверка.** Поздняя отметка меняет только соответствующий пункт. Текущий период и отправленные участникам сообщения сохраняются.

**Статус:** Предложение.

Уточнение. Техническая проверка права на защищённый ресурс относится к доступу к этому ресурсу. Она не должна превращаться в условие отправки сообщений следующего периода. Ранее согласованная проверка конкретного доступа для первой задачи рассматривается отдельно в OQ08.

## Сообщения бадди и руководителю

У бадди и руководителя основной сценарий — получение адресных сообщений о сопровождении стажёра. Общий AI диалог для этих ролей сейчас не требуется. Отметки их пунктов, если появятся, также не управляют периодами.

### FR-SU-01 Сообщение назначенному бадди

Когда действие стажёра требует помощи бадди, система должна отправлять соответствующее сообщение назначенному бадди.

**Проверка.** На этапе доступов бадди получает просьбу помочь конкретному стажёру, а не копию пользовательского чек-листа без пояснения.

**Статус:** Согласовано.

### FR-SU-02 Сообщение руководителю

Система должна отправлять руководителю предусмотренные сценарием сообщения о его участии в текущем периоде стажёра.

**Проверка.** Перед обсуждением промежуточных результатов руководитель получает сообщение о подготовке и предполагаемом действии.

**Статус:** Согласовано.

### FR-SU-03 Контекст сообщения

В сообщении бадди или руководителю должны быть указаны стажёр, период и требуемое от адресата действие.

**Проверка.** Получатель, сопровождающий нескольких стажёров, может определить, кому и с чем нужна помощь.

**Статус:** Согласовано.

### FR-SU-04 Связь сообщений участников

Сообщения стажёру, бадди и руководителю по одному блоку должны формироваться из одного события сценария с разным содержанием по ролям.

**Проверка.** Для одного этапа сообщения относятся к тому же стажёру и периоду и содержат согласованные ссылки и сроки.

**Статус:** Согласовано.

### FR-SU-05 Напоминание о встрече

Система должна напоминать о необходимости обсудить результаты или договориться о встрече с соответствующим участником.

**Проверка.** Напоминание предлагает связаться с руководителем или бадди. Оно не сообщает, что встреча уже назначена, если подтверждённой даты нет.

**Статус:** Согласовано.

| Получатель | Пример сообщения одного этапа |
| --- | --- |
| Стажёр | Пора получить доступы. Вот инструкция и форма. Пройди этот шаг вместе с бадди. |
| Бадди | Помоги стажёру получить нужные доступы и разобраться с инструментами. |
| Руководитель | У стажёра начинается получение доступов. Проверь, нужна ли помощь с согласованием. |

Пример иллюстрирует требования пользователя к сообщению одного этапа. Он не задаёт обязательное время отправки: одновременная доставка и предварительные напоминания уточняются в OQ03.

## Материалы и ответы через RAG

RAG ищет релевантные фрагменты в подготовленных источниках и передаёт их модели для ответа. Контакты и ссылки должны иметь исходный источник. Даты, назначение бадди и маршрутизация рассылок хранятся как данные сценария.

### FR-KB-01 Использование материалов

Система должна использовать подготовленные материалы о компании, команде, инструментах и организационных действиях для поиска ответа стажёру.

**Проверка.** На контрольный вопрос ответ опирается на релевантный разрешённый материал, включённый в базу знаний.

**Статус:** Согласовано.

### FR-KB-02 Фильтрация по правам

Поиск должен выполняться только по источникам, разрешённым текущему стажёру. Недоступные материалы не передаются модели.

**Проверка.** Вопрос о другой команде не раскрывает её закрытые материалы через текст ответа, выдержки или ссылки.

**Статус:** Согласовано.

### FR-KB-03 Ссылки на основания ответа

Ответ должен позволять перейти к использованному источнику или увидеть разрешённую выдержку, если источник предусматривает такую возможность.

**Проверка.** Показанная ссылка соответствует использованному материалу и доступна пользователю.

**Статус:** Согласовано.

### FR-KB-04 Недостаток данных

Если подходящий разрешённый источник не найден, система должна сообщать об отсутствии подтверждённого ответа и показывать известный подходящий контакт при его наличии.

**Проверка.** При вопросе вне базы знаний бот не выдумывает инструкцию, ссылку или имя ответственного.

**Статус:** Согласовано.

### FR-KB-05 Недоступность модели

При сбое модели система должна показать понятное сообщение о невозможности ответа. Отправка сообщений по расписанию должна работать независимо от генерации AI.

**Проверка.** При недоступной модели плановое сообщение из сценария отправляется без вызова модели.

**Статус:** Согласовано.

### FR-KB-06 Обновление базы знаний

Уполномоченный владелец материалов должен иметь способ добавлять, обновлять и исключать источники из поиска.

**Проверка.** После обновления индекса исключённый источник не используется для новых ответов. Роль владельца и способ загрузки определяются в OQ07.

**Статус:** Предложение.

Техническая основа из предыдущей спецификации — React и TypeScript, Go API, PostgreSQL и локальная Qwen через Ollama. Точный механизм поиска, индексирования и обновления RAG ещё требуется спроектировать. Выбор этого механизма не заменяет согласование источников и прав.

## Уведомления и разграничение доступа

### FR-NT-01 Сообщения по расписанию

Система должна инициировать сообщения по опубликованному сценарию без запроса участника к AI.

**Проверка.** Участник, который не отправлял вопрос боту, получает предусмотренное сообщение при наступлении периода.

**Статус:** Согласовано.

### FR-NT-02 Звуковое уведомление

Получение нового сообщения должно сопровождаться звуковым уведомлением в выбранной среде при разрешённых уведомлениях.

**Проверка.** В согласованной среде с включёнными уведомлениями новое сообщение вызывает звук. Поведение при отключённом звуке задаётся в OQ02.

**Статус:** Согласовано.

### FR-NT-03 Защита от повторов

Повторная обработка одного события не должна создавать одинаковые сообщения одному получателю в рамках той же версии сценария.

**Проверка.** Повторный запуск обработки не добавляет второй экземпляр уже созданного сообщения.

**Статус:** Предложение.

### FR-NT-04 Сбой доставки

Система должна сохранять результат попытки доставки и поддерживать повтор при временной ошибке без потери сообщения.

**Проверка.** После восстановления канала сообщение доставляется согласно выбранной политике повторов. Сообщение не помечается прочитанным по факту отправки.

**Статус:** Предложение.

### FR-AC-01 Проверка участника

Система должна определять пользователя и его связь со стажировкой перед чтением переписки, получением сообщений или изменением сценария.

**Проверка.** Пользователь не получает чужую переписку или сообщения чужой стажировки при подстановке идентификатора.

**Статус:** Согласовано.

### FR-AC-02 Приватность сообщений стажёра

Текст сообщений стажёра должен оставаться в его переписке. Автоматическая пересылка этих сообщений руководителю, бадди или HR не предусмотрена.

**Проверка.** В сообщениях участникам по сценарию отсутствуют цитаты или автоматические пересказы вопросов стажёра.

**Статус:** Согласовано.

OQ01 закрыт явным уточнением от 12 ноября 2026 года: личные вопросы и ответы AI не пересылаются. Бадди и руководитель получают отдельные плановые сообщения, соответствующие пунктам стажёра (FR-SU-04).

## Внешние действия и роль HR

### FR-EX-01 Работа во внешних инструментах

В большинстве сценариев бот должен предоставлять инструкцию, ссылку и сведения о помощи бадди для выполнения действия вне продукта.

**Проверка.** Для выбранного блока пользователь получает рабочую ссылку и понимает следующий шаг. Бот не заявляет, что действие уже выполнено.

**Статус:** Согласовано.

### FR-EX-02 Результаты вне продукта

Система должна напоминать стажёру о подготовке и обсуждении результатов. Сами результаты, выводы и проведение встречи выполняются участниками вне продукта.

**Проверка.** Переход к следующему периоду не требует загрузки отчёта, презентации, итогов встречи или их утверждения в боте.

**Статус:** Согласовано.

### FR-EX-03 Отдельный статус интеграции

Если сохраняется прямой вызов сервиса доступа, результат должен определяться подтверждённым ответом сервиса и храниться отдельно от отметки чек-листа.

**Проверка.** Повтор подтверждения не создаёт вторую заявку. При потерянном ответе система восстанавливает ту же операцию.

**Статус:** Условно по OQ08.

В исходном чек-листе HR подтверждает дату старта и контакты, предоставляет организационные материалы и помогает с оформлением. Эти обязанности сохраняются в бизнес-процессе. Способ работы HR в текущем продукте пользователь ещё не уточнил. Следующие требования являются предложениями.

### FR-HR-01 Организационные сведения

Предусмотреть способ передачи HR подтверждённой даты начала и организационных контактов для настройки сценария руководителем.

**Проверка.** Переданные сведения можно использовать при настройке без предоставления HR доступа к личной переписке.

**Статус:** Предложение.

### FR-HR-02 Организационные материалы

Предусмотреть передачу HR ссылок на курсы, документы, инструкции и сроков соответствующих действий.

**Проверка.** Утверждённые материалы доступны для включения в готовые блоки и разрешённые источники знаний.

**Статус:** Предложение.

### FR-HR-03 Сообщения для HR

Если участие HR включается в продукт, предусмотреть адресные сообщения о действиях HR в отношении конкретного стажёра.

**Проверка.** Содержание, периодичность и получатели определены после решения OQ05. До этого обязательная рассылка HR не предполагается.

**Статус:** Предложение.

Кадровое оформление, оценка стажёра и решение о трудоустройстве выполняются людьми. Интеграции с кадровыми системами и автоматизация оформления этим документом не согласуются.

## Объекты и интерфейсы для проектирования

Эта карта показывает, какие объекты и интерфейсы следуют из требований. Она служит исходными данными системного анализа и не задаёт окончательную схему базы данных или количество сервисов.

| Объект | Что необходимо хранить или связывать |
| --- | --- |
| Участник | Идентичность, роль и назначение на конкретную стажировку. |
| Сценарий | Шаблон, стажёр, руководитель, бадди, дата начала и опубликованная версия. |
| Период и блок | Условия наступления, содержание по ролям, ссылки и плановое время сообщений. |
| Сообщение | Тип: плановое или диалоговое; адресат, стажировка, содержание и время. |
| Отметка | Пользователь, конкретный пункт сообщения, состояние и время изменения. |
| Доставка | Событие, получатель, попытка отправки и известный результат доставки. |
| Источник знаний | Материал, область доступа, происхождение и версия для поиска. |

| Интерфейс | Состав |
| --- | --- |
| Переписка стажёра | Вопросы к AI, сообщения периодов, чек-листы, инструкции и внешние ссылки. |
| Сообщения сопровождения | Бадди и руководитель получают адресные сообщения с контекстом стажёра. |
| Конструктор | Готовые блоки, участники, даты, тексты по ролям, предпросмотр и публикация. |
| Вход и привязка роли | Способ идентификации зависит от выбранной среды работы бота. |
| Работа с источниками | Способ загрузки и роль владельца определяются отдельно. |

Для проектирования нужны обработка расписания, формирование сообщений по ролям, доставка, хранение переписки, поиск RAG и проверка прав. Эти обязанности можно реализовать внутри существующего Go API; требование выделять отдельный микросервис для каждой обязанности отсутствует.

Проверка основного пути. Руководитель публикует сценарий → наступает период → создаются адресные сообщения → участники получают уведомления → стажёр переходит по ссылкам или спрашивает AI → следующий период наступает независимо от отметок.

## Вывод

Есть две рабочие части: конструктор сценариев React → Go → PostgreSQL и отдельный Python RAG/MCP → Go ACL → PostgreSQL/Ollama. Главный продуктовый путь «публикация → серверное наступление периода → адресные сообщения → вопрос в основном чате → сохранённый ответ» не собран.

Строго измеримый показатель: **7 из 23 публичных операций Go API реализованы — 30,4% контракта**. Остальные 16 отсутствуют. Это не процент готовности продукта: операции имеют разную сложность. Демо-вход, healthz и внутренние RAG/MCP endpoints не включены в эти 23. README ошибочно сообщает 6/23 и 17 оставшихся.

Из 47 требований 37 помечены в источнике как согласованные, 9 — как предложения, одно — как условное по OQ08. Предложения и условные требования нельзя считать безусловно просроченными обязательствами. Нет оснований объявлять все 97 экранных карточек реализованными функциями или считать число тестов процентом покрытия требований.

## Техническое задание и архитектурные обязательства

- Стек React/TS, Go, PostgreSQL 16/pgvector и отдельный Python RAG реализован. PostgreSQL 16 вместо более раннего предложения 17 — существующий стек репозитория; Go/Python разделение задано пользователем.
- В RAG есть фильтрация до ranking, exact cosine + FTS, snapshots, контроль embedding digest, immutable revision, revoke и повторная ACL-проверка. Это рабочая техническая часть. В репозитории нет полного частного onboarding-корпуса: живой индекс — 28 публичных Markdown, 734 chunks; team fixtures явно синтетические.
- Публикация сценария не пишет outbox. Таблицы outbox_events, EventPublisher и адаптеры Kafka/Clickstream из приложенного ТЗ отсутствуют. Следовательно, нет и потока бизнес-событий для метрик пользы.
- Обещанный набор flags ai_chat/access_integration/sse_delivery/mcp_server/events_publisher отсутствует. VITE_API, DEMO_MODE и выбор RAG_PROVIDER не эквивалентны этому набору.
- Есть провайдеры Ollama и deterministic. OpenAI-compatible адаптера из технического предложения нет. Отдельных трёх runtime skills, роутера/allowlist/hash-loader из RAG SDD в этом репозитории нет; используется один статический SYSTEM prompt. Поля messageContext принимает внутренний API, но реальный Go producer контекста периода/личного сообщения ещё не создан.
- Prometheus-метрики есть у Python RAG/MCP. Go логирует HTTP-технические данные, но полного набора Prometheus для HTTP/scheduler/delivery нет. Отдельной Grafana-конфигурации/бизнес-дашборда нет.
- Docker/CI/Compose реализованы. Для живой модели нужны ручные pull и ingest. CI smoke использует deterministic provider. Живая модель проверена локально в native Windows + WSL, а не как сквозной основной React-чат. Readiness индекса не равна готовности всех зависимостей.
- Нет долговечных AnswerJob/IndexJob/RecipientDelivery/ToolOperation и восстановления их lease/retry после рестарта. Нет формализованных retention/deletion, правил исторического доступа и production-аудита операций.
- Нет измеренного production SLA, p95/нагрузочного отчёта и пилотных метрик бизнес-эффекта. Проверочный локальный ответ на CPU ранее занимал около 43 секунд; это наблюдение одного запроса, не SLA.

## Конкретные дефекты и границы, подтверждённые аудитом

1. **Потеря cutoff после reload.** В Go cutoff_date хранится, но frontend получает его только из ответа publish в ref. При последующей загрузке списка пустой ref превращает afterDate в null. Воспроизведение через реальные функции applyServerScenarios/deliverDue: до reload 0 прошедших сообщений, после reload 2. Это нарушает клиентскую демонстрацию «замена не досылает прошлое» (FR-PL-09/UI-041).
2. **Неверная классификация отсутствия знаний.** Живой вопрос «Как мне оформить отгул на следующую пятницу?» дал HTTP 200, status=unavailable, «попробуй позже», citations=[]. При диагностике модель честно признала отсутствие инструкции, но один из двух предложенных sourceIds отсутствовал среди всех 734 chunks. Проверка источников остановила выдачу; вместо корректного пользовательского no_evidence сработал общий fallback временной ошибки. Это не доказательство безопасности всех отрицательных вопросов, а один воспроизведённый дефект FR-KB-04.
3. **Основной чат не использует RAG.** App.send вызывает demoAnswer после setTimeout(650), без API_ENABLED ветви. В api.ts нет askQuestion/getAnswer. Новая вкладка/устройство не восстанавливает серверную переписку, поскольку её нет.
4. **Общий browser state не является приватностью аккаунтов.** Один ключ homych.frontend.bot.v3 хранит runtimes всех demo-профилей; logout очищает session, но не state/storage. Визуальное скрытие личного чата от бадди не заменяет серверный доступ и очистку/разделение локальных данных.
5. **Назначение бадди не является редактируемой серверной функцией.** bindPlan перезаписывает buddy/lead/team из assignment, таблица назначений заполняется seed; UI-select не создаёт/не меняет назначение. Нужно либо закрепить эту границу в требованиях, либо добавить управляемую операцию.
6. **Документация отстаёт.** В README счётчик API 6/23 неверен; часть спецификаций всё ещё описывает отсутствие сервера/RAG. Код уже содержит Go и отдельный Python модуль, но полной интеграции они не подтверждают.

В ходе аудита код приложения не исправлялся. Указанные дефекты остаются в проверенном commit.

# AI-buddy — передача в разработку и QA

**Историческая редакция.** Для новой разработки использовать [team-specification.md](../product/team-specification.md) и [server-handoff.md](../architecture/server-handoff.md). Старый OpenAPI сохранён отдельно; текущий контракт — проект 23 операций. OQ01 закрыт, чек-листы не блокируют календарь.


**План предыдущей редакции.** Для новой концепции используйте [требования 0.2](../product/functional-requirements.md) и [BPMN версии 3](../processes/bpmn-v3/README.md). T1–T5 и экраны S0–S4 ниже требуют отдельной актуализации перед реализацией новых функций.

[Системная спецификация](system-design.md) · [Роли и границы по 40 шагам](process-scope.md) · [OpenAPI](../architecture/openapi.yaml) · [Каталог BPMN](../processes/bpmn-v2/README.md)

Продакт сверяет результаты и действия участников с листом 3. Техлид проверяет границы прав, схемы данных и условия переходов. QA использует Q01–Q13 как критерии приёмки. Для этапов полной версии Q13 означает разбор процесса с командой. Для MVP предусмотрены автоматизированные проверки API, интерфейса и имитации сервиса.

## Экраны прототипа

| ID | Что видит и делает стажёр | Что происходит после действия |
|---|---|---|
| **S0 · Вход** | Вводит тестовые учётные данные. | A01 открывает сессию. A02 загружает план и ведёт на S1. Если плана нет, экран показывает контакт руководителя, когда он известен. При временном сбое доступен повтор чтения. |
| **S1 · Мой старт** | Видит этап, бадди, три карточки и рекомендуемый шаг. Может выбрать любую карточку и задать вопрос. | A02 даёт сохранённое состояние. A03 добавляет ответ со ссылками и возможным переходом. Выбор карточки остаётся за стажёром. |
| **S2 · Команда** | Открывает каналы, смотрит контакты, отмечает знакомство или откладывает. | A04 сохраняет первое время отметки. Отложить и открыть контакт можно без сохранения. При возврате S1 отражает прогресс. |
| **S3 · Доступы** | Выбирает ресурс, проверяет и при необходимости меняет обоснование, затем подтверждает. После отправки может проверить статус или повторить попытку при неизвестном результате. | A05 сохраняет предпросмотр. A06 возвращает известный статус с номером либо состояние отправки. A07 обновляет статус. При ожидании доступны S1, S2 и просмотр блокера в S4. При отказе доступен контакт бадди. |
| **S4 · Первая задача** | До одобрения нужного ресурса видит блокер, контакт бадди и переход в S3. После одобрения видит постановку, критерии, материалы и кнопку «Готов начать». | A02 возвращает закрытую или открытую карточку. A04 проверяет доступ и сохраняет готовность. Контакт и «Отложить» не меняют прогресс. |

## Проверки и ожидаемые результаты

Для QA подготовить стажёров двух разных команд с планами на 6 и 9 месяцев. У каждого свои источники и задача. У основного аккаунта требуемый ресурс Jira и разрешённый дополнительный ресурс Confluence. Отдельная конфигурация имитации выдаёт отказ на нужный ресурс. Нужны тестовый аккаунт без опубликованного плана и сессия с ролью, отличной от стажёра, для проверки запрета. Тестовые часы и сбои контролируются в тестах, чтобы проверки обходились без ожидания реального согласования.

| ID | Уровень | Сценарий и критерий приёмки |
|---|---|---|
| **Q01** | API и браузер | Оба стажёра видят только свой план, бадди, команду и ресурсы. Чужие `resourceId` и `draftId` в A05–A07 дают одинаковый `404 not_found` с отсутствующими ID. Вызовы не создают попыток. |
| **Q02** | API и браузер | Неверный вход даёт `401 invalid_credentials`. Без cookie и по истечении 8 часов закрытый маршрут даёт 401. Другая роль и чужой Origin на записи дают 403. A02 без опубликованного плана даёт `404 plan_unavailable`, показывает известный контакт, карточки не загружаются. |
| **Q03** | API и браузер | «Отложить» и контакт бадди не создают отметку. S3 доступен до знакомства. Два A04 для `team_intro` возвращают одно время и оставляют одну отметку. После перезагрузки S1 показывает знакомство выполненным и рекомендацию по состоянию доступа. |
| **Q04** | API, интеграция и браузер | A05 возвращает 201. Правка создаёт новый `draftId` с изменённым текстом. До A06 в имитации нет записи. Отмена оставляет `not_requested`. Пробельное обоснование даёт 422. При существующей попытке A05 даёт `409 attempt_exists` с её состоянием. |
| **Q05** | API и интеграция | Две вкладки отправляют один или разные черновики на тот же ресурс одновременно. В БД одна попытка, в имитации один номер. Повтор читает результат с тем же номером и исходными параметрами. `retry` без попытки или по другому черновику даёт `409 retry_not_available`. |
| **Q06** | Интеграция и браузер | Сбой БД до фиксации даёт 503, внешний вызов отсутствует. Потеря ответа до создания заявки даёт 202 и `submitting`, повтор создаёт заявку. Потеря после создания или сбой сохранения даёт 202, A07 восстанавливает номер или A06 повторяет тот же ID. Проверить также потерю ответа между UI и API, перезагрузку и восстановление исходного черновика из A02. |
| **Q07** | Интеграция и браузер | A07 без попытки возвращает `not_requested` и `serviceAvailable: null` без вызова сервиса. При недоступности сервиса показывает сохранённый снимок с `false`. При `pending` остальные карточки доступны. Запоздавшая ревизия и противоречивый ответ не откатывают известное одобрение. |
| **Q08** | API, модель и браузер | Отказ показывает причину при наличии и контакт бадди. Ни `pending`, ни `denied`, ни одобрение Confluence не открывают постановку для Jira. A04 даёт `409 access_required`. A02 и вход A03 не содержат закрытой постановки, критериев и источников задачи. |
| **Q09** | Интеграция и браузер | A07 сохраняет одобрение Jira, A02 возвращает открытую задачу. «Готов начать» проверяет тот же ресурс внутри операции сохранения. После двух A04 и перезагрузки видна одна отметка с исходным временем. После выполнения трёх шагов следующий шаг — контрольная точка. |
| **Q10** | API, модель и браузер | Ответ по своей команде содержит разрешённые источники. Чужие источники и ресурсы из промпта или ответа адаптера не попадают в результат. При отсутствии источника или тайм-ауте A03 возвращает `kind: fallback` без источников и предложения ресурса. В ожидании карточки открываются, чат не записывает прогресс и не отправляет заявку. |
| **Q11** | Демо и интеграция | На чистом запуске без внешнего ключа проходят все три сценария. После перезапуска с тем же томом сохранены прогресс, известный номер и возможность повтора для неопределённой отправки. Отдельный прогон проверяет режим с локальной моделью. |
| **Q12** | Демо и CI | В трёх последовательных прогонах фиксируются среда и время открытия карточки, показа формы и сохранения отметки. Каждое простое действие занимает менее 1 секунды. Дедлайны адаптеров — 10 и 3 секунды. Отчёт показывает строго больше 80% строк, журналы фиксируют технические события без cookie, паролей, обоснований и текстов материалов. |
| **Q13** | Разбор процессов | Пройти P00, P01, P08–P13 с ролями из листа 3. Для обоих сроков планы редактирует и публикует руководитель. Проверить обе ветки учебной практики, утверждение целей на экваторе, критерии финала, передачу задач и состояния «решение известно» и «ожидается». У переходов указаны ответственный, результат и допустимая роль AI. |

## Задания для разработки с Codex

| ID | Владельцы и зависимости | Критерии готовности |
|---|---|---|
| **T1 · Сессия и план** | Бэкенд и фронтенд. Начальная задача. | Миграции и тестовые данные для разных команд, A01–A02, S0–S1. Q01–Q02 в части входа и плана. |
| **T2 · Доступы от формы до статуса** | Бэкенд и фронтенд. После T1. | S3, ограничения БД, A05–A07 и HTTP-имитация, включая повтор и сверку ревизий. Q01 для чужих объектов, Q04–Q07. |
| **T3 · Команда и первая задача** | Фронтенд и бэкенд. S2 после T1, готовность S4 зависит от T2. | S2, S4, A04, состояния карточек и пересчёт рекомендаций. Q03, Q08–Q09 в части API и экранов. |
| **T4 · Ответы и режимы модели** | AI, бэкенд и фронтенд. После T1, проверка доступа к материалам по R04 совместно с T3. | A03, общий отбор источников, деморежим и Ollama, Q08 в части чата и Q10. |
| **T5 · Приёмка и запуск** | QA и релиз. После T1–T4. | README приложения и чистый запуск по N04. Сквозной прогон Q01–Q12, отчёт по покрытию и времени. Q13 проводится как отдельное ревью бизнес-процессов. |

Начать реализацию с T1, затем пройти T2 целиком от предпросмотра до восстановления статуса. После этого привязать открытие S4 и проверку готовности к сохранённому одобрению. В задание Codex передавать ID задачи, относящиеся к ней A и R, узлы BPMN и ожидаемые результаты Q. В ревью сверять изменения интерфейса и API с этими ссылками.

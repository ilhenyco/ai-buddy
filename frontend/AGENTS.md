# Prototype Instructions

## Server mode, 12 November 2026

`VITE_API=on` connects the prototype to the Go backend through `src/api.ts`; without it everything stays in localStorage and must keep working. Server mode shows the demo login (`src/Login.tsx`) and takes roles from the server, never from the review switcher. Scenarios (list, create, draft autosave with If-Match, publish with replacement) go through the API and are mapped into AppState by `src/serverScenarios.ts`; other screens stay local until their backend modules exist. Add new calls to `api` and keep server-only behaviour behind `API_ENABLED`.

## Accepted stage-question suggestions, 12 November 2026

Suggestions are product-owned, never configured by the lead. Show three unique randomly chosen questions from the current stage's built-in pool, changing only when the stage changes. Persist the selection per intern in optional v3 runtime.suggestions; reloads, answers, checks, scrolling history and same-stage publications must retain it. Determine the current stage by actual dates of the active published plan, not the latest old delivery snapshot or a draft. Before the first date use startup questions; with no published plan hide them. New library blocks carry internal stageKind; legacy blocks/copies infer the type from IDs (match final-prep before final). Keep the existing mobile horizontal chip scroll and send handler. If a leave/time-off instruction is unavailable, use the existing honest missing-source response and HR contact guidance, never invent corporate policy. The separate QA origin on port 4174 may be used to test future dates without changing the user's history on 4173.

## Accepted scenario-library flow, 12 November 2026

The lead's Scenario tab opens the scenario list, never directly the builder. Support multiple interns and multiple personal variants per intern. Only one published variant per intern drives messages; publishing another explicitly replaces it and leaves the old variant in the list. Drafts autosave independently, can be incomplete, and never drive delivery. Published edits remain drafts until publication. The builder has a back-to-list action, editable scenario name and visible save status. Published variants cannot be reassigned to another intern. The v3 state migrates v2 without deleting the original key or losing history/checks. Histories and busy AI responses are scoped to the original intern. Delivery events/checks use scenario IDs; replacement skips dates on or before its cutoff date, preserves history and only delivers future dates. Intern selection belongs in prototype review controls, not the user's chat UI. Keep the Origination tokens below for the new list, including dark and narrow layouts.

## Explicit user correction, 11 November 2026

The product is an ordinary proactive bot. It sends a short checkpoint/checklist into one chronological conversation when a scheduled date arrives. NEVER add a user-facing period sidebar, roadmap navigation, or separate next-checkpoint dashboard. Keep the suggested questions above the intern composer. The next checkpoint may appear as a short line at the end of a bot message. Buddy and lead receive the corresponding checklist items, rewritten as concrete actions to do together with/help the intern, with a link to the original intern item. A general paragraph is not a substitute for their checklist. Calendar simulation controls belong only in prototype review tools, not in the user's conversation UI. The lead's separate plan constructor remains.

The older public reference https://habr.com/ru/companies/avito/articles/543450/ is historical context; use the team Figma above for current visual choices. Preserve the user's chat-first concept, calendar-driven periods, and role-specific scheduled messages. Checklist marks must never gate periods. Only interns have an AI composer; buddy and lead receive scheduled messages. Meeting results stay outside this product. HR tools and direct access integration remain clearly marked proposals or conditional demos. Private intern questions are not copied to role notifications.

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

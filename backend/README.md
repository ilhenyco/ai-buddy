# Хомыч · backend

Go 1.24, PostgreSQL 16 (с pgvector), одна зависимость — драйвер `lib/pq`. Модульный монолит: один сервис, модули внутри `internal/`.

**Готово: все 23 операции** `docs/architecture/openapi.yaml` и расширения для FRONT и демо (в том же файле с пометками `x-extension`, `x-demo-only`). Тест `internal/app/contract_test.go` проверяет, что у каждой операции контракта есть маршрут. Покрытие тестами ~89 % (порог в CI — 80 %).

| Модуль | Операции | Фоновая работа |
|---|---|---|
| `identity` | sessionContext, демо-вход; внутренний `POST /internal/v1/ai-context` для Python RAG | — |
| `scenarios` | listTemplates, listScenarios, createScenario, getScenario, saveDraft, publishScenario | — |
| `messages` | listMessages, setCheck, listNotifications | планировщик этапов |
| `answers` | askQuestion, getAnswer | worker заданий ответа |
| `suggestions` | getSuggestions | — |
| `sources` | listSources, createSource, getSource, updateSource, excludeSource, getSourceJob | worker индексации |
| `access` | createAccessDraft, confirmAccess, getAccess, getProtectedTask | — |
| `demo` | дата стенда, «Начать демо заново» | — |

Python RAG/MCP — отдельный сервис [`knowledge/`](../knowledge/README.md): Go хранит вопросы, ответы и материалы, Python ищет и генерирует. Без него (`RAG_URL` пуст) всё, кроме ответов AI и индексации материалов, работает, а Хомыч честно сообщает, что поиск не подключён.

## Запуск

```sh
docker compose up --build          # из корня: PostgreSQL, API на :8080, приложение на :8088, мок доступов на :8091
curl localhost:8080/healthz        # {"status":"ok"}
```

Без Docker для API: `make db` поднимает только базу, `make mock` — мок-сервис доступов (в отдельном терминале), `make run` запускает сервис, `make test` гоняет тесты, `make cover` считает покрытие. Переменные окружения описаны в `.env.example`.

### Демо-сценарии

В демо-режиме при старте сервера создаются три сценария (`internal/scenarios/seed.go`). Это происходит **только если в базе ещё нет ни одного сценария**: созданное вручную не трогается. Даты считаются от сегодняшнего дня.

| Сценарий | Стажёр · руководитель | Состояние | Что показывает |
|---|---|---|---|
| Backend · Платформа, 6 мес., старт неделю назад | Саша · Алексей | опубликован, активен | в ленте сразу два сообщения: «Первый день» и «Первая неделя» |
| Backend · Платформа · 9 месяцев, старт через неделю | Маша · Алексей | черновик, у второго блока пустое название | черновик сохраняется, но публикация просит заполнить поля |
| Mobile · стажировка, 6 мес., старт вчера | Кирилл · Ирина | опубликован, активен | изоляция: Алексей не видит этот сценарий, Ирина видит |

Начать демо с чистого листа — кнопка «Начать демо заново» в интерфейсе (`POST /api/v1/demo/reset`, см. ниже) или пересоздание базы:

```sh
docker compose down -v      # -v удаляет том с базой
docker compose up --build
```

Планировщик сразу рассылает наступившие этапы: при входе Саша, Даша и Алексей видят по два сообщения («Первый день», «Первая неделя»), Кирилл и Ирина — одно. Илья и Маша без опубликованного плана — у них «План ещё не опубликован».

Для изменяющих запросов (POST/PUT/DELETE) клиент передаёт `X-CSRF-Token` из `Context`. `Origin` должен совпадать с адресом сервиса или входить в `ALLOWED_ORIGINS`. Роль из браузера сервер не принимает: связи «стажёр — бадди — руководитель» он берёт из таблицы `assignments`.

## Сценарии: что реализовано

| Операция | Правила |
|---|---|
| `GET /scenario-templates` | Шаблоны на 6 и 9 месяцев, экспортированы из `frontend/src/domain.ts` (`makePlan`) в `internal/scenarios/templates.json`. |
| `GET /scenarios` | Только сценарии текущего руководителя. Поиск `q` по названию и имени стажёра, фильтры `all/drafts/published` (могут пересекаться), `counts`, страницы через `cursor` и `limit`. |
| `POST /scenarios` | Неполный черновик из шаблона, даты сдвинуты на `start`. Требует `Idempotency-Key`. Чужое назначение → 404. |
| `GET /scenarios/{id}` | Сценарий другого руководителя → 404. Ответ содержит `ETag`, равный `draftVersion`. |
| `PUT /scenarios/{id}/draft` | Сохраняет неполный черновик, но проверяет структуру, даты, ссылки (только http/https), id и перечисления. `If-Match` со старой версией → 412 `VERSION_CONFLICT`; исключение — повтор того же содержимого (после потерянного ответа), он возвращает 200. `buddyId`, `leadId` и `teamId` сервер подставляет из назначения. Сменить стажёра у опубликованного сценария нельзя: 409 `PUBLISHED_INTERN_LOCKED`. |
| `POST /scenarios/{id}/publications` | Одна транзакция с блокировкой по назначению. Проверки по порядку: версия (412), заполненность (422), `expectedActiveScenarioId` (409 `ACTIVE_SCENARIO_CHANGED`), подтверждение замены (409 `REPLACEMENT_NOT_CONFIRMED`). Затем пишется неизменяемая ревизия, активный вариант переключается. Дата отсечки: при замене — сегодня по `APP_TZ`, при повторной публикации того же варианта — прежняя, при первой публикации — нет. Повтор с тем же `Idempotency-Key` возвращает ту же ревизию. |

Тесты в `internal/scenarios/api_test.go` повторяют на сервере правила из `frontend/tests/scenarios.test.ts`: черновик не меняет публикацию, замена не досылает прошедшие этапы, повторная публикация не сдвигает отсечку, стажёра у опубликованного сценария не сменить. Отдельно проверены параллельные публикации: при одновременной первой публикации трёх вариантов выигрывает ровно один.

## Сообщения по календарю: что реализовано

`internal/messages`. Хомыч сам пишет по датам: наступил этап активного плана — стажёр, бадди и руководитель получают каждый своё сообщение с чек-листом.

**Планировщик** работает внутри сервера: каждые `SCHEDULER_INTERVAL` (по умолчанию 30 с), сразу после публикации сценария и после перемотки демо-даты.

- Берёт активные планы (`scenarios.ActivePlans`) и наступившие этапы с учётом даты отсечки (`scenarios.DueBlocks`).
- На этап создаёт событие (`message_events`) и сообщения (`messages`) в одной транзакции.
- Стажёр получает текст этапа и все пункты. Бадди и руководитель получают своё сообщение, только если у этапа есть их текст и пункты с действием для них.
- **Без дублей.** Событие уникально по `(assignment_id, scenario_id, block_id)`, сообщение — по `(event_id, recipient, role)`. Повторный и параллельный запуск, перезапуск сервера и повторная публикация того же варианта ничего не дублируют.
- **Снимок текста.** Сообщение хранит этап на момент отправки. Правка плана не меняет отправленное, будущие этапы приходят в новой редакции.
- Получатели берутся из назначения в момент отправки. Просроченные этапы (например, после старта задним числом) ставятся на 09:00 своей даты.
- Не зависит от AI и отметок.

| Операция | Правила |
|---|---|
| `GET /assignments/{id}/messages` | Только свои сообщения участника назначения, по времени; отметки текущего пользователя; `activePlan`. Чужое назначение → 404. |
| `PUT /messages/{id}/tasks/{taskId}/check` | Отметка только своего пункта: стажёр — любого пункта своего сообщения, бадди и руководитель — пунктов с действием для них. Иначе 404. Отметки ни на что не влияют: следующий этап придёт по дате. |
| `GET /notifications` | Свои сообщения, новые сверху, заголовок «Хомыч: этап · стажёр». В веб-канале статус `sent`; push и мессенджер — открытый вопрос OQ02. |

**Демо-дата** (только `DEMO_MODE`, нужен вход):

```sh
POST /api/v1/demo/clock {"date":"2026-11-20"}   # «сегодня» = 20 ноября, планировщик сразу досылает этапы
POST /api/v1/demo/clock {"date":null}           # вернуться к реальному времени
GET  /api/v1/demo/clock                         # {"today":"…","shifted":true}
```

Сдвигается только календарь сценариев и планировщика; сессии живут по реальному времени. Сдвиг хранится в таблице `demo_settings` и восстанавливается при старте API, поэтому перезапуск контейнера посреди показа не возвращает дату. Отправленные сообщения при возврате даты назад не удаляются.

**Сброс демо** (только `DEMO_MODE`, нужен вход), модуль `internal/demo`:

```sh
POST /api/v1/demo/reset   # {"today":"…","shifted":false,"created":9}
```

Удаляет всё, что сделано на стенде: сообщения, отметки, заявки на доступ, сценарии и ревизии, ключи идемпотентности и сохранённую дату. Пользователи и назначения остаются. Затем возвращает реальную дату, переводит мок доступов в «одобрение», заново создаёт три демо-сценария и сразу рассылает наступившие этапы.

## Заявка на доступ: что реализовано

`internal/access` + мок внешнего сервиса `cmd/mock-access` (`internal/accessmock`). Кейс требует, чтобы бот не только советовал, но и выполнял действие через сервис: стажёр подаёт заявку на доступ к репозиторию учебного проекта, без одобренного доступа первая задача закрыта.

**Мок-сервис доступов** — отдельный контейнер `mock-access` (:8091). Реальный сервис Авито подключается заменой `ACCESS_SERVICE_URL`, код модуля не меняется.

| Запрос к моку | Ответ |
|---|---|
| `POST /requests` `{correlationId, userId, resourceId, reason}` | `201 {number: "MOCK-1042", status: "pending"}`; повтор с тем же `correlationId` возвращает ту же заявку |
| `GET /requests/{correlationId}` | заявка; через `MOCK_APPROVE_AFTER` (по умолчанию 20 с) статус становится `approved` или `denied`; неизвестная → 404 |
| `POST /admin/mode` `{mode}` | `approve` / `deny` / `lost` — ответ на новые заявки; `lost`: заявка сохраняется, но ответ не приходит (таймаут) |

**Операции API:**

| Операция | Правила |
|---|---|
| `GET /access-resources` | каталог ресурсов (расширение); первой задаче нужен `repo-learning-read` |
| `POST /access-drafts` | только стажёр своего назначения (бадди и руководитель → 403, чужое → 404), известный ресурс и обоснование (иначе 422). `Idempotency-Key`. Черновик живёт 24 ч |
| `POST /access-drafts/{id}/confirm` | `confirmed: true` — явное действие человека, модель его не вызывает. Сначала в одной транзакции сохраняется операция с `correlationId` и статусом `unknown`, потом идёт вызов сервиса (таймаут 3 с). Ответ получен → номер и `pending`; потерян → остаётся `unknown`. Одна заявка на черновик: повтор с тем же или новым ключом возвращает ту же операцию, второй заявки в сервисе нет. Старая версия → 412, просроченный черновик → 409 `DRAFT_EXPIRED` |
| `GET /access-operations/{id}` | видят стажёр, бадди и руководитель назначения. Незавершённый статус сверяется с сервисом по `correlationId`. Заявку, которую сервис точно не получил, отправляет повторно с тем же `correlationId` (сервис не создаст дубль). Сервис недоступен → остаётся последний известный статус. Свежий `unknown` (< 5 с) не сверяется: исходный вызов ещё может идти |
| `GET /assignments/{id}/access-operations` | заявки назначения, новые сверху (расширение: фронт восстанавливает состояние после перезагрузки) |
| `GET /assignments/{id}/protected-first-task` | постановка первой задачи, только при одобренной заявке на `repo-learning-read`; иначе 403 `ACCESS_REQUIRED`. Отметка в чек-листе доступом не считается, остальные сообщения от заявки не зависят |
| `POST /demo/access-mode` `{mode}` | только `DEMO_MODE`: переключает ответ мока (панель «Состояния» на фронте) |

Тесты (`internal/access/api_test.go`) проверяют: одобрение открывает задачу; права и видимость; повтор подтверждения не создаёт вторую заявку (счётчик вызовов мока); потерянный ответ → `unknown` → сверка без повторной подачи; отказ оставляет задачу закрытой; недоступный сервис и повторная отправка с тем же `correlationId`; просроченный черновик.

**Как показать:** войти Сашей → в сообщении «Первая неделя» «Инструкция по доступам» → «Подать заявку на доступ» → «Подтвердить отправку» → номер `MOCK-…` и «на согласовании» → через 20 с «Проверить статус» → «Доступ одобрен», в «Подготовке к первой задаче» открылась постановка с сервера. Отказ и потерянный ответ включаются в «Состояния» → «Ответ сервиса доступов на новые заявки».

## Вопросы к AI: что реализовано

`internal/answers`. Личный чат стажёра с Хомычем хранится на сервере в той же ленте, что и этапы (`messages.kind` = `user` / `assistant`), поэтому история одна на всех устройствах. Бадди и руководитель его не видят.

| Шаг | Как |
|---|---|
| `POST /assignments/{id}/questions {text}` | Только стажёр своего назначения (бадди и руководитель — 403, чужое — 404), до 1000 символов, `Idempotency-Key`. В одной транзакции сохраняются вопрос (сообщение `user`) и задание `answer_jobs`; ответ — `202` с заданием. Не больше 6 вопросов в минуту: `429 RATE_LIMITED` и `Retry-After` |
| worker | Берёт задание с lease (5 мин) через `FOR UPDATE SKIP LOCKED`, вызывает `POST {RAG_URL}/internal/v1/answer` с сервисным токеном. В запрос уходят `subjectId` из сессии, `requestId` = id задания и `messageContext` — текущий этап этого стажёра (не больше 4000 символов, никогда не тексты бадди/руководителя) |
| ответ | Сообщение `assistant` с цитатами и задание `completed` пишутся в одной транзакции и только если worker всё ещё держит задание (номер попытки как fencing token): поздний дубль ничего не запишет |
| `no_evidence`, `conflicting_sources` | Честный ответ без выдумки: «в материалах нет ответа — спроси бадди», «источники расходятся» |
| сбой связи или тайм-аут | До 3 попыток с backoff 5 с → 10 с; затем `failed` и сообщение в чате «вопрос сохранён, напиши бадди» с `errorCode` |
| `unavailable` от сервиса, 401/403/404/422 | Сразу `failed` (`AI_UNAVAILABLE` / `AI_REJECTED`): повтор не поможет, а медленная модель держала бы чат |
| `GET /answers/{id}` | Только автор. FRONT опрашивает раз в 2 с, пока есть ожидающие вопросы; после перезагрузки ожидание восстанавливается из ленты |

Ответ показывает источники: заголовок, раздел и ссылку. Материалы команды имеют ссылку `https://homych.invalid/sources/<id>` — FRONT открывает их внутри приложения.

Настройка: `RAG_URL`, `RAG_SERVICE_TOKEN` (тот же, что у Python), `RAG_CLIENT_TIMEOUT` (больше `RAG_REQUEST_TIMEOUT` сервиса; по умолчанию 270 с).

## Подсказки вопросов: что реализовано

`internal/suggestions`. `GET /assignments/{id}/suggestions` — только стажёру. Текущий этап — последний наступивший блок активного плана (до старта — `prestart`), вид этапа — `stageKind` блока. Три вопроса из пула этого вида выбираются один раз и хранятся в `suggestion_selections`: после ответов и перезагрузок они те же, новый этап даёт новый набор (не повторяющий прежний полностью). Без опубликованного плана — `409 NO_ACTIVE_SCENARIO`. Пулы — продуктовые тексты, те же, что во FRONT.

## Материалы команды: что реализовано

`internal/sources`. Руководитель управляет материалами своей команды, бадди читает, стажёр открывает материал, на который сослался ответ (кроме исключённых).

| Операция | Правила |
|---|---|
| `POST /sources` | Название, текст (до 1 МБ), раздел, `acl.teamIds` — ровно одна своя команда. Сохраняются материал, версия и задание индексации → `202 IndexJob` |
| `PUT /sources/{id}` | `If-Match` с etag (иначе 412). Новая неизменяемая версия; пока она индексируется, ответы используют прежнюю (`versionId`) |
| `POST /sources/{id}/exclude` | `If-Match`. Материал удаляется из индекса, версии остаются; новая версия возвращает его |
| `GET /sources`, `GET /sources/{id}?versionId=` | Список своих команд с поиском `q`; любая прежняя версия |
| `GET /source-jobs/{id}` | `queued → running → ready` или `failed` (`INDEX_FAILED`; `INDEX_DISABLED`, если RAG не подключён) |

Worker индексации отправляет версию в очередь загрузки Python-сервиса (`PUT /v1/documents/{id}`, ключ идемпотентности = id задания), затем следит за её статусом и по готовности делает версию активной. Нужен ключ клиента с правом `documents:write`: `RAG_SOURCES_TOKEN` у Go и его SHA-256 в `RAG_EXTERNAL_CLIENTS` у Python (см. корневой `.env.example`). «Начать демо заново» материалы не удаляет: они уже в индексе и относятся к команде, а не к прогону демо.

## Метрики

Prometheus-метрики API отдаёт `GET /metrics` (текстовый формат Prometheus). Маршрут лежит вне `/api/v1`, сессия не нужна. Фронтовый nginx проксирует наружу только `/api/`, поэтому `/metrics` доступен на порту API (`:8080`) внутри сети, но не через страницу приложения. Пакет — `internal/platform/metrics`, реестр свой, не глобальный.

| Метрика | Тип | Метки | Что считает |
|---|---|---|---|
| `homych_http_requests_total` | counter | `method`, `route`, `status` | запросы к API |
| `homych_http_request_duration_seconds` | histogram | `method`, `route` | время обработки запроса |
| `homych_jobs_total` | counter | `kind`, `outcome` | шаги фоновых заданий |
| `homych_answer_duration_seconds` | histogram | — | сколько сервис ждёт ответ базы знаний (RAG) |

- `route` — шаблон маршрута из `http.ServeMux` (`GET /api/v1/answers/{answerId}`), а не реальный путь, иначе каждый id стал бы отдельной серией. Запрос, который не подошёл ни под один шаблон, получает `unmatched`.
- `kind` — `answer` (ответ на вопрос), `index` (индексация материала), `access` (заявка на доступ). `outcome` — `completed` (задание завершено: ответ сохранён, материал проиндексирован, решение по заявке получено), `failed` (завершено с ошибкой), `retry` (запланирована повторная попытка).
- Считаются только настоящие завершения: опоздавший воркер, который не сохранил ответ, и повторное закрытие уже закрытого задания в счётчик не попадают. Заявка, отклонённая сервисом доступов, — это завершённое задание (`completed`).
- Middleware стоит внутри `httpx.Middleware`, прямо вокруг mux: только там виден `r.Pattern`.
- Модули получают `*metrics.Metrics` полем `Metrics`; `nil` допустим, метрики тогда не собираются.

```sh
curl localhost:8080/metrics | grep '^homych_'
```

Проверка без базы: `go test ./internal/platform/metrics/ ./internal/app/ -run 'Metrics'`.

## Бизнес-события (outbox)

Модули записывают бизнес-событие **в той же транзакции**, что и изменение, в таблицу `outbox_events` (миграция `0009_outbox.sql`, пакет `internal/platform/outbox`). Фоновый relay (`Outbox.Run`, раз в секунду) отправляет неотправленные события пачками по 100 с `FOR UPDATE SKIP LOCKED`; при сбое получателя пачка повторяется с паузой 2 с → 4 с → … → 5 мин. Доставка хотя бы один раз, получатель отбрасывает дубли по `id`. Каталог 14 событий, конверт и метрики пользы — [docs/architecture/events.md](../docs/architecture/events.md).

| `EVENTS_PUBLISHER` | Что делает |
|---|---|
| `log` (по умолчанию) | строка `"msg":"event"` в лог API: `docker compose logs api \| grep '"event"'` |
| `http` | `POST $EVENTS_HTTP_URL` с `{"events":[…]}`, необязательный `Authorization: Bearer $EVENTS_HTTP_TOKEN` |
| `off` | события не записываются, relay не запускается |

- В событиях только идентификаторы, роли и исходы: текст вопроса, ответа или материала не попадает туда никогда (проверяет `TestBusinessEventsOfTheMainPath`).
- Модули получают `*outbox.Writer` полем `Events`; `nil` допустим — событий нет. Новое событие: константа типа в `outbox.go`, вызов `s.Events.Add(ctx, tx, …)` внутри транзакции модуля, строка в каталоге.
- Метрики: `homych_outbox_published_total{type}`, `homych_outbox_publish_failures_total`, `homych_outbox_pending`.

## Как добавить свой модуль

1. Создать `internal/<модуль>/` с типом `Service` и методом `Routes(mux, prefix, auth)`, по образцу `internal/scenarios`.
2. Зарегистрировать модуль в `internal/app/app.go`.
3. Положить схему в `migrations/000N_<модуль>.sql`; уже применённые файлы не менять.
4. При необходимости добавить демо-данные в `seed/<модуль>.sql` (`ON CONFLICT DO NOTHING`).
5. HTTP-тесты писать через `internal/apptest`: `env := apptest.New(t)`, `c := env.Login(t, "u-sasha")`, `c.Do(t, "GET", ...)`. Каждый тестовый пакет получает отдельную чистую базу.

Общие соглашения:
- ошибки — через `httpx.Error` в формате контракта;
- строгий JSON (лишние поля → 422);
- `Idempotency-Key` — через `platform/idempotency`;
- время — только через `platform/clock` (`clock.Manual` в тестах и для перемотки в демо).

## Открытые вопросы и отступления от контракта

- **Расширения контракта** описаны в `openapi.yaml` (`x-extension`): `Message.next`, `FeedPage.activePlan`, `Citation.url`, `/access-resources`, `/assignments/{id}/access-operations`; демо-эндпоинты помечены `x-demo-only`.
- **Материал относится к одной команде.** Сервис знаний ограничивает документ одной областью (`scope=team`); общий для всех материал (`common`) загружается только операторской командой `ingest`.
- **Индексация Playbook (`ingest playbook`) заменяет весь корпус.** Выполнять до добавления материалов через экран.
- **Тексты шаблонов содержат имена «Саша» и «Даша».** Сервер отдаёт их как есть; подстановка имён — на фронте (`personalizeText`).
- **Срок хранения `idempotency_records` не определён.** Пока записи не удаляются.
- **Сервис доступов Авито (OQ08) не известен.** Формат запросов мока — наше предположение; при подключении реального сервиса меняется только `internal/access/client.go`. Мок хранит заявки в памяти: после перезапуска контейнера старые заявки он «забудет», и сверка отправит их повторно с тем же `correlationId`.
- **Список сценариев фильтруется в памяти.** У одного руководителя их немного; при росте нужно перенести фильтрацию в SQL.
- **«Прочитано» (read receipts) не хранится** — в контракте этого нет.
- **Ответ модели на CPU — до минуты.** Чат не блокируется: ответ приходит, даже если закрыть вкладку. Для показа лучше машина с GPU или прогрев модели первым вопросом.
